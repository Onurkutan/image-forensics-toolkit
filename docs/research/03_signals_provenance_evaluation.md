# Classical Signals, Provenance/Watermarks, Evaluation & Fusion for `imgforensics`

Scope note: deep-learning detectors for fully-synthetic, inpainted, and classically-manipulated images are covered by two companion surveys. This document covers everything *around* those classifiers: low-level classical forensic signals, provenance/watermark checks, the evaluation methodology for the whole system, score fusion, and the tooling landscape. Target stack: Windows 11, Python 3.10, RTX 2060 6GB, with Colab/Kaggle as overflow compute. Written 2026-09-09.

## 1. TL;DR

- No single classical signal survives social-media re-encoding (JPEG re-compress + resize + metadata strip); treat every classical signal as **decays-to-uninformative post-laundering**, not binary useless/useful.
- `jpegio` (Apache-2.0, `pip install pyjpegio`) is the practical entry point for DCT/quant-table access on Windows — no compiler needed [verified].
- PRNU has a solid MIT-licensed Python reference (`polimi-ispl/prnu-python`) [verified], but PRNU/Noiseprint/Noiseprint++ (via `TruFor`) are all **research/nonprofit-only licensed** — fine for a portfolio demo, not for redistribution as a commercial tool [verified].
- C2PA is at spec **v2.4 (April 2026)**; adoption is real but fragmented — Leica/Nikon/Canon ship an older v1.4-based path outside the official Conformance Program, and as of mid-2026 **no camera has passed Conformance** [verified, spec.c2pa.org / secondary press].
- `c2pa-python` (MIT OR Apache-2.0, PyPI, v0.37.10 as of 2026-09-04, Python ≥3.10, Windows wheels) is the right verification library for this project [verified].
- **A missing C2PA manifest proves nothing** — it is the overwhelming default state for web-distributed images, real or fake, not evidence of tampering.
- Google's **SynthID Detector portal is still an early-tester waitlist** (journalists/media professionals) as of the primary DeepMind page, not general public access, despite several 2026 blog posts describing it as "public" [verified from primary source, contradicts some secondary sources].
- The most citable, load-bearing evaluation-bias finding for this project's methodology is Grommelt et al. 2024, *"Fake or JPEG? Revealing Common Biases in Generated Image Detection Datasets"* (arXiv:2403.17608) — real=JPEG/variable-size vs fake=PNG/fixed-size turns detectors into JPEG detectors [verified].
- Recent (2025-2026) cross-generator benchmarks show detector rankings are unstable across test sets (Spearman ρ as low as 0.01) and accuracy on modern commercial generators (Flux, Firefly v4, Midjourney v7) can fall to 18-30% — a single-dataset AUC number is not a claim worth making [verified].
- Recommended build order (Section 8): ELA, EXIF/thumbnail/quant-table checks, C2PA verify, copy-move (block-based), double-JPEG/ghost, then PRNU only if a reference camera set exists.

## 2. Classical forensic signals

All costs below are **rough engineering estimates** (order of magnitude, not measured benchmarks) for a ~2MP image on a modern desktop CPU — flagged `[estimate]`, distinct from the `[verified]` library facts.

|---|---|---|---|---|---|

| Resampling / interpolation traces | Local/global scale-rotate-shear | Same EM engine as CFA, no package | n/a | ~100s ms | **No** — JPEG blocking below QF~95 masks the periodicity, and nearly everything below QF95 after upload |
| Copy-move (keypoint SIFT/ORB) | Cloned region, same image | `lambertoballan/sift-forensic`, `andreacos/SIFT-based-copy-move-forgery-detection`, `niyishakapatrick/...-ORB` — vendor-and-adapt, not `pip install` | mixed/unclear | 100s ms-1 s | **Partial** — survives resize better than JPEG-domain signals |
| Copy-move (dense block matching) | Cloned smooth/low-texture region | `rahmatnazali/image-copy-move-detection` ("pimage") and similar | mixed/unclear | 1-5 s | **Partial**, same caveat, slower |

| Photoshop/editor save signatures (APP13 IRB, XMP history, APP14) | Direct editor trail, save/edit history | `exiftool` (most complete parser) [verified]; `python-xmp-toolkit` for XMP/RDF | GPL/Artistic; python-xmp-toolkit varies | tens of ms | **No** — stripped on upload, and even pre-strip it's unsigned so it's evidentiary, not proof |

**Cross-cutting takeaway:** everything JPEG-domain (ELA, double-JPEG, ghosts, blocking-grid, quant-table, CFA/resampling) and everything metadata-based collapses once an image has been through Instagram/WhatsApp/Twitter/X-style re-encoding + strip. Only copy-move (keypoint or block) and PRNU-style pixel-fingerprint methods retain *partial* signal post-laundering, and PRNU needs a reference set the project usually won't have. This is the central design constraint for Section 8.

## 3. Provenance and watermarks

### C2PA / Content Credentials

- **Spec status [verified]:** current technical specification is **v2.4** (spec.c2pa.org, dated ~April 2026); v2.3 (2026-01-05) added CMAF/live-stream signing. C2PA is governed by the Coalition for Content Provenance and Authenticity under the Joint Development Foundation (Linux Foundation), with Adobe driving the Content Authenticity Initiative promotional side. ([spec.c2pa.org](https://spec.c2pa.org/specifications/specifications/2.4/index.html), [Wikipedia: Content Credentials](https://en.wikipedia.org/wiki/Content_Credentials))
- **Who signs at capture/generation [verified, mixed-confidence secondary sources]:** Leica M11-P (Oct 2023, first consumer camera), Sony α9 III/α1 II, Nikon Z6 III (firmware, then suspended after a signing-key vulnerability), Canon (EOS R1/R5 Mark II + 7 more via firmware, July 2025); Samsung Galaxy S25 and Google Pixel 10 on phones. On generators, OpenAI (DALL·E/ChatGPT images) and Google Gemini reportedly hold Conformance certification; Adobe Firefly, Stability AI, and Runway support C2PA without formal certification. **As of mid-2026, no camera has passed the official Conformance Program** — hardware adoption is running ahead of interoperability testing.
- **Offline verification:** a C2PA manifest is a signed, embedded (or remotely-referenced) claim chain; verification checks the signature against a trust list and the content hash against the asset — this runs fully offline once a trust-anchor list is cached locally (only OCSP/revocation checking needs network access, and can be soft-failed).
- **`c2pa-python` [verified, PyPI]:** v0.37.10 released 2026-09-04, requires Python ≥3.10, ships prebuilt wheels for Windows/Linux/macOS (x86-64 and ARM64), dual-licensed MIT OR Apache-2.0 — a clean fit for this project's Python 3.10/Windows constraint, no Rust/C toolchain needed locally. Exposes a `verify_from_file_json`-style call that returns a manifest report. ([pypi.org/project/c2pa-python](https://pypi.org/project/c2pa-python/))
- **What a missing manifest means — and doesn't:** absence of a C2PA manifest is the *default* state for the vast majority of images on the internet today (most cameras, all older photos, and every image re-encoded by a platform that strips metadata) — it is **not** evidence the image is fake or manipulated. Conversely, a *present and valid* manifest only proves provenance-chain integrity ("this bit-for-bit content came from claimed source X, unmodified since signing") — it does not assess whether the depicted scene is true, and known attacks (e.g. the Nikon Z6III key-compromise case, root-level Android exploits) show a valid signature can be attached to content that misrepresents its origin. Treat C2PA as a **corroborating provenance check**, not a detector.

### Invisible watermarks

| Scheme | Owner | Offline-checkable with open code? | Notes |
|---|---|---|---|
| SynthID | Google DeepMind | **No, gated** — the SynthID Detector portal is in an early-tester phase (journalists/media professionals, waitlist) per the primary DeepMind page; some secondary 2026 articles describe broader rollout (Search/Chrome integration, 100B+ items marked, OpenAI/ElevenLabs partnership) but this is verification-*surfaced-through-Google's-own-UI*, not an open detector you can run offline [verified: gated; secondary reports of wider integration, lower confidence] | Text watermarking variant was open-sourced (Hugging Face, 2024); the image detector is not |
| Stable Signature | Meta AI (FAIR) | **Yes, code available** — `facebookresearch/stable_signature` [verified, GitHub] | Only works on latent-diffusion models fine-tuned with the signed decoder; noncommercial license; robust to ~90% crop per the paper; known removal attacks exist (arXiv:2405.07145, "Stable Signature is Unstable") |
| Tree-Ring | UMD/Wen et al. | **Yes, code available** — `YuxinWenRick/tree-ring-watermark` [verified, GitHub] | Requires inverting the diffusion process to check the noise pattern — needs access to (or a good approximation of) the generating model, so it's a generator-side self-check more than a universal offline verifier |
| `invisible-watermark` (used by Stable Diffusion / SDXL) | ShieldMnt (community) | **Yes** — `ShieldMnt/invisible-watermark`, DWT+DCT / DWT+DCT+SVD / RivaGAN methods [verified, GitHub] | This is the *encoder* SD/SDXL ships by default; useful for **checking whether an image came from a vanilla SD/SDXL pipeline that didn't disable it** — many users/tools explicitly disable it, so absence proves nothing |

Practical implication for `imgforensics`: only **Stable Signature**, **Tree-Ring**, and the **`invisible-watermark`** package give this project actual runnable, offline, open-source detection code in 2026. SynthID and IMATAG are check-through-their-portal-only. Treat all watermark checks as **presence-only, generator-specific** signals (a hit is strong evidence; a miss proves nothing, since watermarking is opt-in, strippable by re-encoding/cropping in many schemes, and many generators don't watermark at all).

## 5. Evaluation methodology

**Metrics.** Report AUC-ROC and Average Precision (AP) as primary ranking metrics (robust to class imbalance, which this project will have — real images vastly outnumber any one fake category). Report balanced accuracy and accuracy-at-fixed-threshold (e.g., threshold chosen on a held-out calibration split at a fixed FPR, such as 1% or 5%) since a bare accuracy number at an arbitrary 0.5 threshold is close to meaningless for imbalanced forensic tasks. Report calibration via Expected Calibration Error (ECE) — recent work flags that ECE is sensitive to its binning scheme and recommends debiased/equal-mass estimators rather than naive equal-width bins. For any component that outputs a mask (inpainting/splicing localization), report pixel-level F1 and IoU against ground-truth masks, not just image-level accuracy.

**Cross-generator and cross-dataset protocols.** Train/validate on one set of generators/manipulation tools and test on held-out ones never seen in training — same-generator evaluation produces near-saturated (>98%) accuracy that collapses (to roughly 60-70% average, and as low as 18-30% against 2025-2026 commercial generators like Flux Dev, Firefly v4, Midjourney v7) under cross-generator testing. Recent 2025-2026 benchmark work also shows **detector rankings are not stable across test sets** — Spearman rank correlation between rankings on different benchmark pairs has been measured as low as ρ≈0.01, with up to a 37-point spread between best and worst detector on one benchmark. Consequence for `imgforensics`: never report a single-dataset number as "the" accuracy; report a matrix (train-source × test-source) or explicitly label results as within-distribution.

**Robustness suite.** Build a fixed, versioned perturbation battery applied at eval time to every test image: JPEG re-encode at quality factors spanning 50-95 in steps of ~5-10; resize by factors from 0.5× to 2× (both directions, since upscaling and downscaling stress different artifacts); Gaussian blur at 2-3 sigma levels; random/center crop retaining 50-90% of area; and simulated platform pipelines (e.g., resize-to-platform-max-dimension + re-encode at the platform's typical JPEG quality + metadata strip, approximating WhatsApp/Twitter-X/Instagram behavior — exact platform QFs shift over time and aren't officially published, so treat these as configurable presets, not certified reproductions). Report AUC/AP degradation curves against severity, not just a single averaged robustness number.

**Dataset leakage and shortcut pitfalls.** The load-bearing citation here is Grommelt, Weiss, Pfreundt & Keuper, **"Fake or JPEG? Revealing Common Biases in Generated Image Detection Datasets"**, ECCV 2024 Workshops (arXiv:2403.17608): using GenImage, they show real images are JPEG and variably-sized while synthetic images are uniformly PNG and fixed-size, and detectors trained on such splits partly degenerate into JPEG/format/resolution detectors rather than generation-artifact detectors; they propose rebalancing format and resolution between classes as a fix. Complementary 2024-2025 work reinforces the same class of pitfall: content/source bias (real and fake sets drawn from different scene distributions, e.g. LAION-derived prompts vs. COCO photos), duplicated images across train/test splits inflating reported accuracy, and mismatched JPEG-quality/size *distributions* even when the two classes nominally use "the same" format (arXiv:2412.17671, "A Bias-Free Training Paradigm for More General AI-generated Image Detection"; arXiv:2409.14128, "Present and Future Generalization of Synthetic Image Detectors"). For `imgforensics`, the actionable rule is: **never let file format, resolution distribution, or JPEG quality distribution correlate with the label** in any train or eval split; enforce this with an automated split-auditor rather than manual review, and treat any held-out set that fails the audit as unusable for reporting.

## 6. Score fusion for heterogeneous detectors

The system will emit scores from very different sources: classical signal scores (ELA anomaly score, copy-move match ratio, PRNU correlation), deep classifiers (from the companion surveys), and provenance/watermark hits (near-binary). Fusion needs to handle this heterogeneity without letting any one noisy classical signal dominate.

- **Weighted average** — simplest baseline; weights set manually or by per-signal validation AUC. Fast, easy to explain, but brittle: one miscalibrated signal (e.g. a copy-move detector firing on repetitive texture) can swing the average even where it shouldn't apply.
- **Calibrated logistic stacking** — fit a small logistic-regression (or shallow GBM) meta-model on a held-out validation split, using each detector's *calibrated* score (Platt/temperature-scaled per-detector first) as a feature. This is the standard approach in multi-forensic-tool fusion literature, where per-tool output maps are stacked and a small model learns the combination rather than hand-tuned weights.
- **Handling abstain/uncertain** — many classical signals are only *applicable* to a subset of inputs (PRNU needs a reference fingerprint; CFA/resampling need a non-laundered JPEG). The fuser must accept per-signal "not applicable" rather than a forced 0 or 0.5 — otherwise an inapplicable signal silently biases the fused decision. Use a missing-indicator feature per signal, or a gate keyed on cheap metadata (is this a JPEG? is there EXIF? is there a reference camera set?).
- **Avoiding overfitting the fuser** — the meta-model has few features but is exactly where cross-generator leakage re-enters if its validation split overlaps in source/content with the reporting set; fit and freeze the fuser on one split, report on a disjoint cross-generator/cross-dataset split (Section 5), and keep it small (logistic regression, not a deep net) given the likely validation-set size for a solo-developer project.
- **Explanation output** — per-signal "cards" (score + applicability + a one-line rationale, e.g. "ELA: high local error concentration around subject boundary") are more honest than one opaque fused number, especially since several signals are non-discriminative post-laundering; for the deep-classifier component, Grad-CAM-style heatmaps give a visual complement. Ship the card table *alongside* any fused score, not instead of it.

## 7. Deployment patterns (brief)

- **Gradio** demo for interactive single-image exploration (upload → per-signal cards + heatmaps); deploy free on Hugging Face Spaces (CPU by default, GPU tier paid) — a natural fit for a portfolio project.
- **FastAPI** service for programmatic/batch use, with the same underlying pipeline; keep classical signals and any deep model behind the same request path so the fusion logic isn't duplicated.
- **Hugging Face Hub** for hosting any trained fuser weights or fine-tuned watermark/classifier checkpoints — free, versioned, works well with `huggingface_hub` for programmatic download at app startup.
- **ONNX export** for CPU inference of any neural component (Noiseprint CNN, classifiers from the companion surveys) so the Gradio/FastAPI deployment doesn't require a GPU; ONNX Runtime has broad pre-quantized model support and is the standard path for shipping a CPU-only inference story on a project that develops on an RTX 2060 but should demo without one.

## 8. Recommendations for this project

**Implement first (cheap, explainable, in rough build order):**

1. **EXIF/metadata + thumbnail-mismatch + quant-table checks** — near-zero cost, `exiftool`/Pillow only, and gives an instant "was this even attempted to be laundered" signal even though it's non-discriminative once stripped.
2. **C2PA verify via `c2pa-python`** — a few lines, MIT/Apache-2.0, directly answers a provenance question the other signals can't, and is on-brand for a 2026 portfolio project.
3. **Error Level Analysis** — trivial to implement on Pillow, genuinely useful as a *visual* explanation artifact even where it's not a strong standalone classifier.
4. **Quantization-table camera/software matching** — near-free once quant tables are already being read for double-JPEG work; reuses the same `jpegio`/Pillow call.
5. **Copy-move (block-based, e.g. DCT/Zernike block hashing)** — the strongest classical signal that partially survives resizing/recompression; more robust than the keypoint variant on smooth cloned regions common in retouching.
6. **JPEG ghosts / double-JPEG histogram check** — moderate implementation effort but reuses the `jpegio` investment from #4 and is a well-documented, explainable algorithm (good for a portfolio write-up).
7. **`invisible-watermark` decode pass** — free applicability check for "did this come from an un-modified SD/SDXL pipeline"; cheap to bolt on given the maintained package.

**Use these libraries:** `exiftool` (via `pyexiftool`) for metadata, `jpegio` for DCT/quant access, `c2pa-python` for provenance, `polimi-ispl/prnu-python` only if a genuine multi-image reference-camera set is available (otherwise skip — PRNU without a reference fingerprint is not runnable), `ShieldMnt/invisible-watermark` for the SD/SDXL check, Pillow/OpenCV for the hand-rolled classical signals.

**Skip, and why:**
- **CFA/demosaicing and resampling/interpolation EM-based detectors** — no maintained package, high implementation cost (paper-to-code), and the failure mode (uninformative on non-Bayer/social-laundered images, which is most of the target distribution) undermines the payoff.
- **Chromatic aberration** — weak even on pristine images; low value for the engineering cost.
- **Noiseprint++/TruFor as a production component** — research/nonprofit-only license blocks anything beyond a labeled demo; fine to cite and even run for a portfolio showcase, but don't build the core pipeline's dependency on it.
- **SynthID as an offline check** — currently gated behind Google's own waitlist portal; there is nothing to integrate locally in 2026, so treat it as "future work" rather than a v1 feature.
- **Ghiro, FotoForensics** — dead/closed respectively; reference-only.

**Building the robustness suite:** implement it as a deterministic, versioned augmentation pipeline (fixed random seeds per severity level) separate from any training-time augmentation, so the *same* perturbed test set can be regenerated for every model/version compared. Store the perturbation parameters (JPEG QF list, resize factors, blur sigmas, crop fractions, "platform preset" definitions) in a single config file inside the repo so results are reproducible and the presets can be tuned later without silently changing what "robustness" means across experiment runs. Pair every robustness number with the cross-generator/cross-dataset protocol from Section 5 — a detector that is both cross-generator-generalizable and robust to recompression/resize is the actual bar; either alone is not sufficient evidence for a portfolio claim of "works on real-world images."
